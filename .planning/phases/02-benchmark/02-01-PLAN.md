<design_decisions>
Settled before planning; do not revisit during execution.

**The fixture is TypeScript, written in a deliberately legacy style.** The brief mandates
"TypeScript throughout" and proving the engine on a synthetic fixture before wiring ARAG.
A TS fixture also means Verify (Phase 4) can generate and run real tests with no extra
toolchain. The known limitation: an 80% score on TypeScript says little about extraction
from C# or VB.NET, which is what the real targets (`Claims.BE`, `Lawsys_Desktop`) are
written in. A small real-C# probe belongs in Phase 3 once Discover exists — note it, do
not build it here.

**It lives at `fixtures/legacy-claims/`, outside the pnpm workspace.** `pnpm-workspace.yaml`
globs only `apps/*` and `packages/*`, so a root-level `fixtures/` directory is not a linked
package. That is deliberate: the real target is an external read-only repo, not a workspace
sibling. Making the fixture a workspace package would let Phase 3 and 4 quietly assume
in-workspace resolution and then break on first contact with a real target.

**Domain is legal-expenses insurance** (claims authorisation and disbursements, BTE/ATE,
UK/CA variants, panel solicitors). It mirrors the actual ARAG estate, so the answer key and
the eventual ARAG transition are both realistic.
</design_decisions>

<task type="auto">
  <name>Task 1: Legacy-styled claims code with planted rules</name>
  <files>fixtures/legacy-claims/src/authorise-claim.ts, fixtures/legacy-claims/src/disbursements.ts, fixtures/legacy-claims/src/types.ts, .prettierignore</files>
  <action>
Write two modules of runnable but deliberately legacy-grade TypeScript. They must be valid
TS that executes (Phase 4 runs generated tests against them and Phase 6 proves equivalence),
but must NOT be clean code. Required characteristics — these are the extraction difficulty,
so do not tidy them:

- One long function per module with deeply nested `if`/`else` and early returns, rather than
  small composed functions
- Magic numbers inline with no named constants (authorisation threshold `10000`, lapse
  window `45`, BACS cutoff hour `15`)
- Stringly-typed status codes (`'A'`, `'P'`, `'R'`, `'X'`) with no enum
- Country branching (`'UK'` / `'CA'`) with subtly different thresholds per market
- A DAS / non-DAS insurer-brand split, as `Claims.BE` has

Plant these specific, findable rules:
1. **Dark logic — at least 3 rules present only in code**, absent from the docs written in
   Task 3. E.g. a secondary seniority check that only applies to CA claims; a silent cap on
   counsel fees; a weekend-shift on the BACS cutoff.
2. **A genuine contradiction with the docs** — the code applies a **45**-day lapse window.
   Task 3's wiki will state 30 days. Neither file may hint that the other is wrong.
3. **A dead branch** that can never execute — a check against a status value (`'X'`) that
   nothing in the codebase or seed data ever sets. This is the "never-executed" half of Dead
   Rules.
4. **Duplicated logic that has silently diverged** — the panel-solicitor check appears in
   both modules with one differing threshold. A real contradiction *within* the code, not
   between code and docs.
5. **A stale comment that contradicts the code beneath it** — e.g. `// senior sign-off over
   £5,000` above a check that actually uses `10000`.

Add `.prettierignore` at the repo root containing `fixtures/` — **this is important**.
`pnpm format` globs `**/*.{ts,tsx,md}` and would reformat the fixture, shifting line numbers.
The answer key in 02-02 pins provenance to specific lines, so a reformat would silently
invalidate the entire benchmark.

Do not add a `package.json`, `tsconfig.json` or any build script here. The fixture is read
material, not a buildable package, and adding a tsconfig would pull deliberately-bad code
into `pnpm check-types` — which is already red for unrelated reasons (ISS-001/002/004).
  </action>
  <verify>`npx tsc --noEmit --skipLibCheck fixtures/legacy-claims/src/*.ts` reports no errors (the code is bad, not broken); `pnpm check-types` is unchanged from its current state; `git check-ignore -v` confirms `.prettierignore` covers the fixture</verify>
  <done>Two modules exist with all five planted categories present; the code type-checks in isolation; prettier will not touch it</done>
</task>

<task type="auto">
  <name>Task 2: SQL schema and seed data carrying their own rules</name>
  <files>fixtures/legacy-claims/db/schema.sql, fixtures/legacy-claims/db/seed.sql</files>
  <action>
Write plain SQL Server-flavoured DDL and inserts. Rules must be encoded in the *shape* of
the schema and the *content* of the data, not in comments — extraction from schema and data
origins is the point.

`schema.sql` must carry at least **2 schema-origin rules**:
- A `CHECK` constraint encoding a business limit (e.g. `settlement_amount <= 250000`)
- A `NOT NULL` column plus a foreign key implying a mandatory relationship (e.g. every
  authorised claim must reference a handler)
- Optionally a naming/column convention implying a rule, as the Lawsys DB does

`seed.sql` must carry at least **2 data-origin rules** — regularities that hold across every
row but are stated nowhere in code or docs. E.g. no claim in market `'CA'` ever has a
disbursement over a certain value; every claim with status `'A'` has a non-null
authorisation date. These are the rules only a data pass can find.

Critically: **no row may ever set status `'X'`**, so Task 1's dead branch stays genuinely
unreachable.

Keep it small — roughly 3 tables and 20-30 rows. The fixture must be readable end to end by
a human reviewing the answer key.
  </action>
  <verify>Both files are syntactically valid SQL (review by reading; no database is required to run them in this phase); no seed row uses status `'X'`; the CHECK constraint value does not contradict any seeded row</verify>
  <done>3 tables with at least 2 schema-encoded rules; 20-30 seed rows with at least 2 data-only regularities; status `'X'` unused</done>
</task>

<task type="auto">
  <name>Task 3: Stale docs and the planted-rule manifest</name>
  <files>fixtures/legacy-claims/docs/underwriting-wiki.md, fixtures/legacy-claims/docs/handler-guide.md, fixtures/legacy-claims/PLANTED.md</files>
  <action>
Write the documentation as a wiki that was accurate three years ago and has drifted since.
It must contain:

- **The contradiction**: a 30-day lapse window, against the code's 45. State it plainly and
  confidently, the way a real stale wiki does.
- **At least 3 dead rules** — rules described in the docs that exist nowhere in the code or
  schema. E.g. a "provisional cover" step that was removed; a second-signature requirement
  that no longer applies.
- **Correct overlap** — several rules that genuinely match the code. If the docs were
  entirely wrong, classification would be trivial.
- **Omissions** — say nothing about Task 1's dark-logic rules.

Then write `PLANTED.md`: the authoritative record of what was planted, one row per rule.
Columns: intended id (`R-001`…), one-sentence statement, where the evidence is (file + line),
intended `origins`, intended classification (`dark-logic` / `dead-rule` / `contradiction` /
`normal`), and expected difficulty (`easy` / `medium` / `hard`).

Write this manifest **as the rules are planted**, not reconstructed afterwards — a
reconstructed manifest will miss rules and the answer key inherits the gap. Target **24-30
rules total**, so each is worth ~3-4% and the 80% threshold has finer resolution than the
scoring granularity.

Required minimums across the manifest: ≥3 `dark-logic`, ≥3 `dead-rule`, ≥2 `contradiction`
(the docs/code lapse window and the code/code panel divergence), ≥2 `schema` origin, ≥2
`data` origin.

`PLANTED.md` is the fixture's answer sheet. It is committed deliberately — this is a
synthetic benchmark, not a held-out test set, and Discover never reads it.
  </action>
