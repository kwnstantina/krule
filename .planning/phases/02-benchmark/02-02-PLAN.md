<design_decisions>
Settled before planning; do not revisit during execution.

**Matching is hybrid with cached verdicts.** Provenance overlap (file + line range) pairs a
discovered rule with an answer-key candidate; a Claude judge then confirms the two
plain-language statements mean the same thing; every verdict is cached to a checked-in file.
Deterministic-only matching would score wording rather than understanding, and would credit
keyword stuffing. Judge-only matching would make the benchmark drift run to run — an
unacceptable property for a tool whose entire pitch is provable output. The cache gives both:
reruns replay recorded judgements, only genuinely new pairs cost a call, and a human can
audit the cached verdicts.

**The Claude judge implementation lands in Phase 3, not here.** The LLM provider abstraction
is `03-01`, and the brief requires provider abstraction from the start — building a direct
Anthropic call here would duplicate work and then need unpicking. This plan ships the `Judge`
interface, the cache, and a deterministic default implementation, so the harness is complete
and testable end to end. That costs nothing in practice: there is no discovered output to
score until Discover exists in Phase 3 anyway. `03-01` supplies the real judge.
</design_decisions>

<task type="auto">
  <name>Task 2: Provenance pairing and precision/recall scoring</name>
  <files>packages/benchmark/src/pairing.ts, packages/benchmark/src/score.ts, packages/benchmark/src/pairing.test.ts, packages/benchmark/src/score.test.ts</files>
  <action>
`pairing.ts` — pair discovered rules to answer-key rules by provenance overlap:
- Same `file`, with line ranges overlapping (treat a bare `line` as `[line, line]`, and
  respect `endLine` where present)
- Allow a tolerance of ±3 lines, since an extractor may anchor a rule to the `if` or to the
  body. Make the tolerance a named exported constant, not a literal buried in a comparison.
- A discovered rule may only be consumed by one key rule and vice versa. Where several
  candidates overlap, prefer the tightest line-distance match. Return the unpaired remainder
  on both sides — those are the false positives and false negatives.

`score.ts` — compute from the pairing plus judge verdicts:
- `truePositives` (paired AND judged semantically equivalent), `falsePositives`,
  `falseNegatives`
- `precision`, `recall`, `f1`
- A per-classification breakdown driven by the `class:` tags: recall for dark-logic,
  dead-rule, contradiction and normal separately. **This matters more than the headline
  number** — 85% overall while missing every dark-logic rule would mean the tool fails at
  the thing it is sold for, and a single figure would hide that.
- A `meetsThreshold` boolean against a named `PASS_THRESHOLD = 0.8`

A rule paired by provenance but rejected by the judge counts as **both** a false positive and
a false negative: the extractor found the right location but described the wrong rule, which
is worse than silence in an audit artifact. Document that in a comment — it is a deliberate
choice, not an accounting accident.

Test with hand-built inputs, not real Discover output (there isn't any yet): a perfect match,
a total miss, partial credit, off-by-two line anchoring inside tolerance, off-by-ten outside
it, and a contested overlap where two candidates compete.
  </action>
  <verify>`pnpm --filter @repo/benchmark test` passes; scoring a synthetic perfect match yields precision 1, recall 1, `meetsThreshold` true; scoring an empty discovery yields recall 0</verify>
  <done>Pairing handles tolerance, contention and one-to-one consumption; scoring reports precision/recall/f1 plus a per-classification breakdown; judge-rejected pairs are counted on both sides</done>
</task>

`judge.ts`:
- Export a `Judge` interface: `equivalent(discoveredStatement, keyStatement): Promise<{ equivalent: boolean; reason: string }>`
- Export `createCachedJudge(inner: Judge, cachePath: string): Judge` — looks up a stable key
  (a hash of the two statements, order-fixed) and only calls `inner` on a miss, then persists.
  The cache file is JSON, checked in, and **sorted by key on write** so diffs are reviewable
  and merge conflicts are legible.
- Export `deterministicJudge`: normalises case/punctuation and compares significant-term
  overlap above a named threshold. This is the default until `03-01` lands the Claude judge.
  Its docstring must say plainly that it is a placeholder and will under-credit paraphrase —
  so nobody mistakes an early score for a real one.

`report.ts` — render a scored result as text: headline precision/recall/f1, PASS/FAIL against
the threshold, the per-classification table, and explicit lists of missed rules (with their
ids and difficulty) and false positives. A benchmark that reports only a number is unusable
for improving prompts in Phase 3; the miss list is the actionable part.

Wire the whole path into `src/index.ts` as `scoreKontractAgainstKey(discoveredPath, keyPath, judge)`
so `03-03` can call one function.
