<task type="auto">
  <name>Task 2: Define the kontract schema</name>
  <files>packages/kontract/src/schema.ts, packages/kontract/src/index.ts</files>
  <action>
Define with Zod, inferring types from the schemas (the pattern `@repo/core/src/types.ts`
already uses — schemas are the single source of truth, never hand-written interfaces
alongside them).

`ProvenanceSchema`:
- `file` (string, required) — repo-relative path
- `line` (int, positive, required)
- `commit` (string, required) — the sha the rule was read at, so drift detection in Phase
  5 has a baseline to diff against
- `endLine` (int, optional)

`RuleStatusSchema`: enum `['verified', 'unverified', 'contradicted', 'drifted']`.
Default `'unverified'` — a rule is untrusted until Verify says otherwise, which is the
brief's core discipline ("no rule enters the model without a code reference + generated
test").

`RuleOriginSchema`: enum `['code', 'schema', 'data', 'docs']`. Rules carry `origins` as a
non-empty array. Phase 5 derives its report sections from this: origins containing only
`code` = Dark Logic; only `docs` = a Dead Rule candidate. Include it now even though
Discover does not exist yet — retrofitting a required field across four consumers later is
the expensive path.

`KontractRuleSchema`:
- `id` (string matching `/^R-\d+$/`) — the brief's CI drift message is literally "this PR
  changes rule R-114", so the format is a requirement, not a preference
- `statement` (string, min length ~10) — the rule in plain language
- `provenance` (array of `ProvenanceSchema`, non-empty) — a rule can be evidenced in more
  than one place
- `confidence` (number, 0 to 1 inclusive)
- `origins` (non-empty array of `RuleOriginSchema`)
- `status` (`RuleStatusSchema`, defaulting to `'unverified'`)
- `tags` (array of string, optional)
- `notes` (string, optional)

`KontractDocumentSchema`:
- `kontractVersion` (literal `1`) — a version discriminator from day one, so later schema
  changes are detectable instead of ambiguous
- `module` (string) — what was discovered
- `generatedAt` (ISO datetime string)
- `commit` (string) — the sha of the target repo at extraction time
- `rules` (array of `KontractRuleSchema`)

Add a refinement rejecting duplicate rule ids within a document — duplicate ids would make
the Phase 5 drift diff ambiguous and are cheap to catch here.

Do NOT add an executable-rule field (a `@repo/core` `Rule`) yet. Phase 6 migrates one rule
family and will know then what the right linkage is; guessing now bakes in a wrong shape.
Re-export everything from `src/index.ts`.
  </action>

  <done>All schemas defined with inferred types exported; ids constrained to `R-\d+`; status defaults to `unverified`; duplicate ids rejected</done>

<task type="auto">
  <name>Task 3: YAML load/save with round-trip tests</name>
  <files>packages/kontract/src/io.ts, packages/kontract/src/index.ts, packages/kontract/src/io.test.ts, packages/kontract/src/schema.test.ts</files>
  <action>
In `io.ts` export:
- `parseKontract(yamlText: string): KontractDocument` — `YAML.parse` then
  `KontractDocumentSchema.parse`. Let the `ZodError` propagate; do not catch and return a
  partial document. Phase 3's self-correcting generation loop (see
  `packages/ai-service/src/rule-generator.ts`) feeds validation errors back into the
  prompt to retry, so it needs the structured error, not a swallowed one.
- `serializeKontract(doc: KontractDocument): string` — validate first, then `YAML.stringify`.
- `readKontractFile(path)` / `writeKontractFile(path, doc)` — thin `node:fs/promises`
  wrappers over the two above.

Tests:
1. **Round trip** — a fixture document with two rules, multiple provenance entries, mixed
   origins and every one of the four statuses: `parse(serialize(doc))` deep-equals `doc`.
2. **Rejection cases**, each asserting a `ZodError`: a bad id (`RULE-1`, `R-abc`),
   `confidence` of `1.5` and `-0.1`, empty `provenance`, empty `origins`, an unknown
   `status`, and two rules sharing an id.
3. **Status default** — a rule parsed without `status` comes out `'unverified'`.
4. **Comment preservation** — serialize a document, hand-add a `#` comment to the YAML,
   parse and re-serialize, and assert the comment survives. This is the reason `yaml` was
   chosen over `js-yaml`; if it does not hold, the choice needs revisiting and that belongs
   in the summary.

Write the fixture inline in the test file rather than as a separate `.yaml` asset — Phase 2
builds the real fixture corpus, and a stray sample file here would compete with it for
authority.
  </action>
  <verify>`pnpm --filter @repo/kontract test` passes all tests; `pnpm test` from root includes the new package</verify>
  <done>Round trip, every rejection case, the status default, and comment preservation all pass</done>
</task>
